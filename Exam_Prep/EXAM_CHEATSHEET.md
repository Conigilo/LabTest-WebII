# 🔥 คัมภีร์ลับก่อนสอบ (Exam Cheat Sheet)

จากประสบการณ์ ทฤษฎีและข้อสอบมักจะออกลึกกว่าแค่การเขียนโค้ดให้รันผ่าน นี่คือ "จุดตาย" (Pitfalls) และ "คำถามยอดฮิต" ที่เจอประจำในข้อสอบ:

## 1. หมวด REST API & Swagger

### 🔴 จุดตายข้อ 1: ใช้ HTTP Status Codes ผิด
อาจารย์มักตรวจว่าเราส่ง Status Code กลับมาสมเหตุสมผลหรือไม่
*   **200 (OK):** ใช้ตอน GET สำเร็จ, PUT/DELETE สำเร็จแบบส่งข้อมูลกลับ
*   **201 (Created):** ใช้ตอน **POST สำเร็จ** (แปลว่าสร้างตัวตนใหม่ในระบบสำเร็จ ห้ามใช้ 200 เด็ดขาด)
*   **400 (Bad Request):** User ส่งข้อมูลมาผิดพลาด ซอร์สโค้ดดีแต่ข้อมูลไม่ครบ (เช่น ลืมส่งชื่อหนังสือมา)
*   **401 (Unauthorized):** ยังไม่ได้ Login หรือ Token ไม่มี
*   **403 (Forbidden):** Login แล้วแต่ "สิทธิ์ไม่ถึง" (เช่น เป็น User แต่พยายามลบหนังสือ)
*   **404 (Not Found):** หา ID ที่ส่งมาไม่เจอใน Database
*   **500 (Internal Server Error):** โค้ดพัง Database ล่ม (มักอยู่ในบล็อก `catch`)

### 🔴 จุดตายข้อ 2: รับตัวแปรผิดที่ (Params vs Query vs Body)
*   `req.params.id` 👉 ดึงจาก Path ของ URL (เช่น `/books/1` เข้าใจแบบเจาะจงตัว)
*   `req.query.search` 👉 ดึงจากหลังเครื่องหมายปรัศนีใน URL (เช่น `/books?search=Harry` ใช้ทำ Filter/ค้นหา/เรียงลำดับ)
*   `req.body` 👉 ดึงจากกล่องซ่อนตัวที่ส่งมา มักใช้กับ POST/PUT ที่ข้อมูลเยอะๆ เช่น ชื่อ/ราคา

## 2. หมวด gRPC

### 🔴 คำถามยอดฮิต: "ทำไมต้องใช้ gRPC แทน REST API?"
ถ้าอาจารย์ให้เปรียบเทียบ ให้ตอบตาม Key points นี้:
1.  **เร็วกว่า และไฟล์เล็กกว่า:** เพราะ gRPC คุยกันด้วยภาษาเครื่อง (Binary: Protocol Buffers) ไม่ได้ส่งมาเป็นข้อความแสนยาวเหมือน JSON ใน REST
2.  **มี Type ชัดเจน (Type-safety):** ไฟล์ `.proto` เป็นสัญญาบังคับให้ส่งข้อมูลตรงเป๊ะๆ ทำให้ฝั่ง Client หรือ Server จะแอบมั่วส่งเกิน/ส่งขาดไม่ได้ ลดบัค
3.  **วิ่งบน HTTP/2:** ทำให้สามารถเชื่อมต่อทีเดียวแล้วส่งข้อมูลไปกลับหลายๆ รอบได้ (Streaming) ในขณะที่ REST (HTTP/1.1) มักจะเป็นการยิงไปแล้วจบเป็นครั้งๆ

## 3. หมวด ORM (Prisma)

### 🔴 คำถามยอดฮิต: "ORM ดียังไง ทำไมไม่เขียน SQL ตรงๆ?"
1.  **ป้องกัน SQL Injection:** การเขียน SQL ตรงๆ อาจโดนแฮกเกอร์แอบเติมคำสั่งลบ Database ทิ้งได้ (เช่น `SELECT * FROM users WHERE id = X OR 1=1`) แต่ ORM จะจัดการหนีบ Escape string ป้องกันให้เราเรียบร้อยแล้ว
2.  **เขียนง่าย ซ่อมง่าย:** ถ้าในอนาคตเปลี่ยนใจจาก SQLite ไปใช้ PostgreSQL ก็แทบจะไม่ต้องแก้โค้ดเลย (แค่แก้ไฟล์ตั้งค่าเชื่อมต่อ) เพราะ ORM จะแปลงภาษา JS ของเราไปเป็น SQL ของระบบนั้นให้เอง!

### 🔴 ความสัมพันธ์ฐานข้อมูล (Relations)
อาจารย์อาจมีโจทย์ให้ทำ 1 User มีหลาย Books (1-to-Many). ใน Prisma คุณต้องระบุความสัมพันธ์ให้ชัดใน `schema.prisma`. แปะตัวอย่างเผื่อไว้:
```prisma
model User {
  id    Int    @id @default(autoincrement())
  books Book[] // สื่อว่า 1 คน มีหลายเล่ม
}
model Book {
  id     Int  @id @default(autoincrement())
  userId Int
  owner  User @relation(fields: [userId], references: [id]) 
}
```

## 4. หมวด Auth & Security

### 🔴 จุดตายข้อใหญ่ที่สุด (ถ้ามีสอบเรื่องนี้): **ห้ามเก็บ Password เป็นแบบ Text ธรรมดาลง Database เด็ดขาด!!**
ในข้อสอบถ้าใช้ Password แบบพิมพ์ตรงๆ (Plaintext) เช่น `"password123"` อาจโดนหักคะแนนยับ! คุณต้องใช้ **"การเข้ารหัสผ่าน (Hashing)"** เช่นใช้ไลบรารี่ `bcrypt`
*   **ขาขึ้น (Register):** รับพาสเวิร์ดมา -> นำมา Hash (สับให้เละ) ด้วย `bcrypt.hash()` -> เก็บตัวที่เละแล้วลงก้อน DB
*   **ขาลง (Login):** รับพาสเวิร์ดที่คนพิมพ์มา -> ใช้รหัสที่เละๆ ใน DB มาเทียบกันเบื้องหลังด้วย `bcrypt.compare()`

### 🔴 คำถามยอดฮิต: "โครงสร้างขอ JWT มีอะไรบ้าง?"
JWT (JSON Web Token) ประกอบด้วย 3 ส่วน คั่นด้วยจุด (`.`)
1.  **Header:** บอกวิธีการเข้ารหัสที่ใช้
2.  **Payload:** ข้อมูลฝังไว้ (เช่น `id`, `role`) **ข้อควรระวัง:** ห้ามฝัง Password รหัสผ่านหรือข้อมูลที่ละเอียดอ่อนมากๆ ลงไปเด็ดขาด! เพราะใครๆ ก็สามารถเอา Token ไป Decode อ่าน Payload ได้
3.  **Signature:** กุญแจลับ (ลายเซ็นผู้ประทับตรา) เอาไว้เช็คว่า Token นี้ไม่ได้ถูกใครไปแอบแก้ไข Payload มานะ!
